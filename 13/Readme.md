## Part 1｜主題課程：RAG 架構與企業智慧問答系統

### 一、為什麼企業不能只靠 LLM 內建知識回答問題

在企業情境中，若僅依賴語言模型本身的內建知識，會面臨兩類實務問題：

1. **知識時效性不足**：模型無法掌握最新的內部規定或文件版本（模型的訓練資料有截止日期，也從未看過企業的內部文件）。
2. **生成內容不可驗證**：即使回覆語句流暢，仍可能與內部制度不符，甚至「一本正經地說錯話」——這種現象稱為**幻覺（Hallucination）**。

要讓回答真正「以資料為依據」，企業應用多會採用**檢索增強生成（Retrieval-Augmented Generation, RAG）架構**，讓語言模型在生成回覆前，先取得可引用的外部資料來源。

### 二、RAG 系統運作流程

RAG 透過結合「文件檢索」與「語言生成」兩個機制運作，大致流程如下：

1. 使用者提出問題（可能透過 LINE、企業內部通訊軟體等前端介面）
2. 系統將問題轉換為向量，在企業的知識庫（文件、規章、SOP）中檢索最相關的段落
3. 把檢索到的段落，連同原始問題一起交給 LLM
4. LLM 依據檢索到的「有憑有據」的內容，生成最終回覆，而不是單純憑內建知識瞎猜

**這個設計解決了什麼問題**：知識時效性問題被解決，因為只要更新知識庫文件，系統立刻就能引用最新資訊，不需要重新訓練模型；內容可驗證性問題也被緩解，因為回覆是「有依據」的，甚至可以附上引用來源，方便使用者查證。

### 三、知識圖譜：補強關係型問題的查詢能力

知識圖譜（Knowledge Graph）是一種以「節點（實體）」與「邊（關係）」表示知識結構的方式。例如：「達文西」創作了「蒙娜麗莎」，「蒙娜麗莎」被收藏於「羅浮宮」，羅浮宮則位於「巴黎」——這種關係鏈，讓系統不只能回答「蒙娜麗莎在哪裡展出」，還能進一步推論其所屬城市與文化背景。

知識圖譜的優點，在於能直接支援**關係型問題**的查詢與推理，例如「某位員工隸屬哪個部門，該部門的主管是誰」，這類問題若只靠關鍵字搜尋或向量檢索，往往需要使用者自行整合多筆資料才能得到答案。當知識圖譜與 RAG 架構結合，系統一方面能透過向量檢索取得相關文件內容作為事實依據，另一方面也能利用知識圖譜補足實體之間的關係與結構化脈絡，讓系統不僅「答得出來」，也能「說得清楚來源與關聯」。

### 四、企業智慧問答系統的三大關鍵設計

| 設計 | 功能 |
|---|---|
| 前端通訊介面設計 | 以 LINE、企業通訊軟體或內部聊天平台為入口，讓使用者在熟悉的溝通環境中直接提問，降低使用門檻 |
| 檢索增強生成（RAG）設計 | 在語言模型生成回答前，先從企業內部文件與資料庫中檢索相關內容，確保回覆有據可查，降低幻覺風險 |
| 知識圖譜設計 | 將人員、部門、流程與制度等關係型知識以結構化方式保存，補強關係推理與跨文件整合能力 |

透過這三種設計的搭配，生成式 AI 不再只是「能對話的模型」，而是能在企業知識治理與流程支援中，成為可靠的智慧助理，特別適合行政詢問、內部規定查詢、SOP 說明、跨部門資訊一致化等情境。

## Part 2｜Vibe Coding 實作演練：搭建一個最簡化的 RAG 雛形

### 範例①　用自己的文件建立一個簡易問答系統

**題目定義**：不需要複雜的資料庫或框架，用幾段你自己企業的（模擬）內部規章文字，體驗 RAG「先檢索、再生成」的最小可行版本。

**給 AI 的提示詞：**
```
請用 Python 幫我做一個最簡化的 RAG 雛形：
1. 建立一個知識庫，內容是 5 段關於「員工請假規定」的模擬文字
   （例如：特休天數規則、病假需附證明的規定、請假流程等，內容可自行編寫）
2. 用 sentence-transformers 套件的 all-MiniLM-L6-v2 模型，
   把這 5 段文字轉換成向量，並存起來
3. 讓我輸入一個問題（例如「病假需要附診斷證明嗎？」），
   系統計算這個問題與 5 段知識庫文字的相似度，找出最相關的 1-2 段
4. 把找到的段落與原始問題一起組成一個提示詞，印出來
   （這個提示詞就是接下來要送給 LLM 生成最終答案的內容）
請給我可以在 Google Colab 直接執行的完整程式碼。
```

**預期產出的程式碼骨架：**
```python
!pip install sentence-transformers --quiet
from sentence_transformers import SentenceTransformer, util

knowledge_base = [
    "員工特休天數依年資計算，滿一年可享有 7 天特休，滿三年增加為 10 天。",
    "請病假需檢附合格醫療院所開立之診斷證明，單次病假超過 2 天須提前告知主管。",
    "事假每年上限 14 天，超過部分將不予支薪。",
    "請假流程須於系統內填寫申請單，並經直屬主管核准後方為生效。",
    "特休未休完可於年度結束後折算工資，但公司鼓勵員工於當年度休畢。",
]

model = SentenceTransformer("all-MiniLM-L6-v2")
kb_embeddings = model.encode(knowledge_base, convert_to_tensor=True)

question = "病假需要附診斷證明嗎？"
question_embedding = model.encode(question, convert_to_tensor=True)

scores = util.cos_sim(question_embedding, kb_embeddings)[0]
top_idx = scores.argsort(descending=True)[:2]

retrieved = [knowledge_base[i] for i in top_idx]
print("檢索到的相關段落：", retrieved)

prompt = f"""請根據以下資料回答問題，若資料中沒有答案，請明確說明查無相關規定。

資料：
{chr(10).join(retrieved)}

問題：{question}
"""
print("\n組成的提示詞：\n", prompt)
```

**延伸練習**：把知識庫換成自己企業真實（或模擬）的另一份規章，測試 5 個不同問題，觀察檢索結果是否都準確找到對應段落；如果檢索錯誤，思考是不是文字描述得不夠明確。

### 範例②　體驗「沒有 RAG」vs.「有 RAG」的差異

**題目定義**：把同一個問題，分別直接問 LLM（沒有提供任何資料）與帶著檢索到的段落問 LLM（範例①組成的提示詞），比較兩次回答的可信度差異。

**操作方式**：把範例①最後印出的「組成的提示詞」，貼到 ChatGPT / Claude / Gemini；同時另外開一個新對話，直接問「病假需要附診斷證明嗎？」（不提供任何資料）。比較兩次回答——沒有資料時，AI 可能會給出一個「聽起來合理但未必符合你公司規定」的通用答案；有資料時，AI 的回答會明確引用你提供的規定。

**管理意涵**：這正是 RAG 架構的商業價值所在——它不是讓 AI 變得更聰明，而是讓 AI 的回答「有憑有據」，這對於企業內部知識管理、法遵文件查詢等場景至關重要。
