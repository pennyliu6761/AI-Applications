## Part 1｜主題課程：AI 專案評審的四個面向

### 一、技術可行性：資料、模型與團隊能力的三角關係

一個 AI 專案是否技術可行，取決於三者是否匹配：

| 要素 | 檢查重點 |
|---|---|
| **資料可得性** | 需要的資料公司內部有沒有？資料量夠不夠？品質如何（呼應第 3 週商業問題轉譯表）？ |
| **模型複雜度** | 這個問題是不是一定要用複雜模型才能解決？（呼應第 3 週「模型越複雜不代表越好用」） |
| **團隊能力** | 內部有沒有維護這套系統的人才？若沒有，是否有可靠的外部廠商或雲端服務可以支援？ |

**常見誤區**：許多專案在提案階段只討論「模型準確率能不能達標」，卻沒有評估「資料能不能持續穩定取得」——一個上線時表現良好、但半年後資料來源斷絕或改版的系統，仍然是失敗的專案。

### 二、財務可行性：ROI 試算與隱性維護成本

第 6 週我們練習過「傳統抽檢 vs. AI 全檢」的 ROI 試算，但完整的財務評估，還必須把**隱性維護成本**納入，這是企劃書中最容易被低估的部分：

| 隱性成本類型 | 說明 |
|---|---|
| **模型飄移（Model Drift）** | 資料分布隨時間改變（例如消費行為隨經濟環境變化），模型準確率會逐漸下降，需要定期重新訓練 |
| **監控與維運** | 需要有人持續監看系統是否正常運作、預測結果是否合理，而不是上線後就放著不管 |
| **提示詞維護（GenAI 情境）** | 隨著 LLM 版本更新，原本設計好的提示詞可能需要重新調整（呼應第 12 週提示工程） |
| **資料治理成本** | 隨法規變動（呼應第 2 週 AI 基本法／AI Act），可能需要持續調整資料蒐集與保存方式 |

**管理意涵**：一份只算「建置成本」不算「維運成本」的 ROI 試算，往往會高估專案的財務吸引力，導致上線後才發現「養不起」。

### 三、組織可行性：團隊阻力的來源與因應

AI 專案失敗，很多時候不是技術問題，而是組織問題。常見的阻力來源包括：

- **取代焦慮**：第一線員工擔心 AI 上線後自己的工作被取代，因而消極抵制或不配合資料蒐集
- **流程慣性**：既有的工作流程已經運作多年，改變流程本身就有學習成本與心理抗拒
- **信任落差**：黑盒子模型（呼應第 6 週）讓使用者不理解、不信任系統的判斷，寧可繼續用舊方法
- **權責不清**：AI 輔助決策後，若出錯的責任歸屬沒有講清楚，第一線人員可能不敢真正依賴系統的建議

**因應做法**：清楚溝通 AI 的角色是「輔助決策」而非「取代人力」；讓受影響的員工參與系統設計初期的討論，而不是最後才被告知；針對黑盒子問題，優先在可解釋性較高的環節導入 AI，建立信任後再擴大範圍。

### 四、整合評審框架

把以上三個面向整理成一個簡單的評分邏輯，可以在企劃提案階段快速篩選專案的優先順序：

```
專案總評分 = 技術可行性分數 × 權重 + 財務可行性分數 × 權重 + 組織可行性分數 × 權重
```

各面向的權重可以依企業文化調整——技術能力強但組織文化保守的企業，可能要把「組織可行性」的權重拉高，避免選到技術上可行、但落地時處處碰壁的專案。

## Part 2｜Vibe Coding 實作演練：AI 專案評審計算機

### 範例①　打造一個簡單的專案評分計算機

**題目定義**：把 Part 1 的整合評審框架寫成一個可重複使用的小工具，輸入各面向的評分，自動算出總分與建議。

**給 AI 的提示詞：**
```
請用 Python 幫我做一個簡單的「AI 專案評審計算機」：
1. 讓我輸入以下四個面向的分數（1-10 分）：
   資料可得性、模型可行性、財務投資報酬、組織接受度
2. 讓我可以自訂四個面向的權重（總和需為 100%），
   若沒有輸入則使用預設權重：資料可得性 30%、模型可行性 25%、
   財務投資報酬 25%、組織接受度 20%
3. 計算加權總分（滿分 10 分），並依總分給出建議：
   8 分以上：建議優先執行
   6-8 分：建議先做小規模試點
   6 分以下：建議重新評估或暫緩
請給我可以在 Google Colab 直接執行的完整程式碼。
```

**預期產出的程式碼骨架：**
```python
def project_evaluation(data_score, model_score, roi_score, org_score,
                        weights=(0.3, 0.25, 0.25, 0.2)):
    scores = [data_score, model_score, roi_score, org_score]
    total = sum(s * w for s, w in zip(scores, weights))

    if total >= 8:
        recommendation = "建議優先執行"
    elif total >= 6:
        recommendation = "建議先做小規模試點"
    else:
        recommendation = "建議重新評估或暫緩"

    print(f"加權總分：{total:.2f} / 10")
    print(f"建議：{recommendation}")
    return total, recommendation

# 範例：填入你自己專案的評分
project_evaluation(data_score=7, model_score=6, roi_score=8, org_score=5)
```

**延伸練習**：把自己期末企劃報告的專案，實際填入四個面向的評分，看看系統給出的建議是否符合你自己的直覺判斷；如果不符合，思考是評分不準確，還是權重設定需要調整。

### 範例②　用 AI 幫忙腦力激盪「隱性維護成本」清單

**題目定義**：針對自己的專案，請 AI 協助列出容易被忽略的隱性維護成本項目，作為財務評估的補充檢查清單。

**給 AI 的提示詞：**
```
我的 AI 導入專案是：[描述你的專案，例如「用機器學習模型預測客戶流失」]

請幫我列出這類專案上線後，容易被低估的隱性維護成本，
包含但不限於：資料更新頻率、模型重新訓練頻率、系統監控人力、
法規遵循的持續成本。請針對我的專案情境給出具體的項目與概估頻率。
```
